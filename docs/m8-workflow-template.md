# M8 通用定时巡检工作流模板（bug 源可换）

> 目标：把"定时拉任务源 → 子 agent 排查 → 修复 → 通知"的值班模式抽象成通用模板，适配任何 bug/工单源。

## 痛点

- bug 巡检、值班排查全靠人肉盯群 / 盯 bug 系统，费神易漏。
- 市面工具绑定特定系统（TAPD/Jira/飞书项目），换一家就废。

## 设计思想（与 bug 源无关）

无论 TAPD、Jira、飞书项目还是邮件群，工作流骨架相同：

```
┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐
│ 定时拉取  │ →  │ 去重判定  │ →  │ 子 agent  │ →  │  闭环处理 │
│ 任务源    │    │ (新单?)  │    │ 隔离排查  │    │ 修复/通知 │
└──────────┘    └────────────┘    └──────────┘    └──────────┘
     ↑ 每 N 分钟一次，无新单静默                        │
     └──────────────── 会话内定时驱动 ←────────────────┘
```

四个抽象点：

1. **任务源适配器**：bug 单从哪里来，怎么拉。不同系统只换这一层。
2. **新单判定**：按单号 + 状态感知去重（新增 / 重新打开 / 新评论都算"新活动"）。
3. **子 agent 隔离**：一单一 agent，上下文互不污染；主会话只做汇总与决策。
4. **处理闭环**：真代码问题 → 修复；非代码问题 → 不改代码，加评论 + 通知；敏感操作（改库、发布）必须人工确认。

## 你的 skill 骨架（占位符版）

保存到 `~/.pi/agent/skills/<your-workflow-name>/SKILL.md`：

```markdown
---
name: <your-workflow-name>
description: 定时巡检 <任务源>，发现 <事件> 后自动 <处理动作>，并通知 <对象>。
---

# <名称>

## 触发
用户说"开始 <名称> 巡检"时启动；启动后按 <间隔> 定时轮询（建议 20-30 分钟）。

## 任务源（唯一需要替换的适配层）
- 来源：<TAPD / Jira / 飞书项目 / 邮件 / 群消息>
- 拉取方式：<MCP 工具 / API / CLI / 消息流>
- 鉴权：<cookie / token / OAuth——敏感信息不入仓库>

## 新单判定
- 按 <单号 + 状态> 去重。
- 这些都算新活动：状态变 NEW / 重新打开 / 新增评论。

## 处理闭环
1. 拉取 → 2. 去重 → 3. 一单一子 agent 排查
4. 判定（代码问题 / 非代码问题）→ 5. 修复 + 验证 → 6. 通知 <对象> + 更新状态

## 环境注意
- 线上问题用生产最新基线分支分析，别用本地旧分支。
- 多环境（云/地域）注意区分。

## 边界（强制）
- 仅当前会话执行（sessionOnly），会话关闭即停止，重开会话重新启动。
- 无新单静默。
- 敏感操作（改库 / 发布 / 群发消息）必须先经用户确认。
```

## 引导式创建（skill 中的流程）

1. 问清三要素：任务源？触发方式（推荐定时轮询）？处理闭环（修复后通知谁/更新什么状态）？
2. AI 生成个性化骨架 → 用户确认 → AI 落盘到 `~/.pi/agent/skills/<name>/SKILL.md`
3. 配套创建一个 sessionOnly 定时任务（间隔建议 20-30 分钟）
4. 建议安装 M7 状态栏插件，可视化任务状态

## 一个真实场景的填充示例

> 以"TAPD bug 自动修复"为例（占位符替换后）：

- 任务源：TAPD 某 workspace 的指定需求关联 bug
- 新单判定：状态 NEW / reopened / 有新评论
- 处理闭环：子 agent 读 bug + 需求上下文 → 定位代码 → 修复 → 提交 → 发布测试环境 → 通知测试 + 更新 bug 状态
- 边界：发布与改库前必须用户确认；仅当前会话执行

## 验证

- 手动触发一次巡检，确认拉取 → 去重 → 排查 → 通知链路跑通
- 无新单时静默，有新单时才输出
