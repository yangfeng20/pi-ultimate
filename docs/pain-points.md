# 痛点与使用场景

> 本文回答一个问题：**pi-ultimate 到底解决了什么问题？**
> 每个痛点都来自真实的日常开发场景，对号入座看看你中了几条。

## 使用场景画像

如果你符合以下任意一条，这个仓库就是为你准备的：

- 🪟 **Windows 用户**：想让 AI 帮你干活，但 AI 执行命令时各种乱码、卡死、报错
- 🇨🇳 **国内用户**：AI 访问 GitHub / 搜索国外资源频繁失败，开全局代理又影响国内访问
- 🔍 **项目越大越卡**：AI 一搜索就扫 node_modules，一跑命令就无限等待，一个会话被拖死
- 👨‍💻 **值班 / 巡检岗**：每天人肉盯 bug 系统、盯工单群，重复排查同类问题
- ⏰ **想自动化**：想让 AI 定时干活（巡检、汇总、提醒），但定时任务总"失忆"或"串台"

## 基础层：6 个每天都在发生的痛点

### 1. 命令执行：Windows 三大经典惨案

**场景一**：你让 AI 查个日志，它好心帮你 `type app.log`，中文全是乱码。你说"用 chcp 65001 换成 UTF-8"，还是乱码。

**场景二**：AI 用 PowerShell 读一个 UTF-8 的配置文件，中文注释变成 `ɰ` 这样的天书。你以为文件坏了，其实是 PowerShell 默认按 GBK 解码。

**场景三**：AI 要执行一条带复杂参数的命令，引号嵌套到三层，用 `\"` 硬转义，结果命令在第一层就被截断，执行了一个完全不同的东西。

**后果**：你花在"解释为什么乱码"上的时间比干活还多。AI 每次新会话都重新踩一遍坑。

**pi-ultimate 的解法**：一次性配置 Git Bash 通道 + 编码规范 + 引号策略，写进 AI 的长期记忆（AGENTS.md），AI 从此不再踩坑。[→ M1 文档](m1-command-execution.md)

### 2. TUI 模式：滚屏和输入框打架

**场景**：AI 输出了一段很长的分析，你想往上翻看，结果输入框跟着滚走了；或者你翻到一半想补句话，聊天区域自动跳回最底部。

**后果**：长输出场景下基本没法优雅地"边看边聊"。

**pi-ultimate 的解法**：开启 fullscreen 模式，输出区独立滚动、输入框固定底部（sticky 效果），接近主流 Agent CLI 的手感。[→ M2 文档](m2-tui-mode.md)

### 3. 命令超时：一条卡死的命令拖垮整个会话

**场景**：AI 跑了一条命令，其实已经卡死（比如网络不通的 curl），但它就一直在那儿等着。你去喝茶回来，发现 20 分钟过去了，会话还挂在那条命令上。

**更隐蔽的**：AI 有时会设置 30000 秒的超时——名义上有超时，实际等于没有。

**pi-ultimate 的解法**：注入超时规范（搜索类 ≤180s、其他 ≤300s、禁止省略、超时就换方案），AI 执行命令前先想"会不会卡死、卡了怎么办"。[→ M3 文档](m3-timeout.md)

### 4. 搜索工具链：grep 扫 node_modules 卡到怀疑人生

**场景**：AI 在一个前端项目里 `grep -r "keyword" .`，扫完 node_modules 花了 3 分钟，刷出几千行第三方库的匹配，真正想找的那行淹没在噪音里。

**后果**：慢 + 噪音大 + AI 上下文被垃圾信息灌满。

**pi-ultimate 的解法**：装 rg（ripgrep，自动跳过产物目录、多线程）+ 注入"grep 必须排除产物目录"的兜底规范。[→ M4 文档](m4-grep.md)

### 5. 命令别名：高频长命令重复输入

**场景**：`git log --oneline -10`、`git status`……一天敲几十遍。让 AI 干活没问题，自己手动操作时就难受了。

**pi-ultimate 的解法**：一套推荐别名集 + AI 引导写入你的 shell 配置。[→ M5 文档](m5-alias.md)

### 6. 代理设置：访问国外资源失败，又不想开全局代理

**场景**：AI 要查个 GitHub issue / 下载个国外包，直接失败。你开了全局代理，结果访问国内站点反而变慢了，公司内网也受影响。

**pi-ultimate 的解法**：按需代理——把代理信息写进 AGENTS.md，AI 只在访问国外资源时自动带上，国内/内网直连。[→ M6 文档](m6-proxy.md)

## 增强层：把 AI 从"工具"变成"同事"的 3 个工作流

### 7. pi-subagents：主会话不堪重负 + 定时任务串台

**场景一**：你让 AI 排查一个线上问题，它查日志、查数据库、读代码……主会话上下文塞满了中间过程，越聊越慢，关键信息被淹没。

**场景二**：你创建了一个定时巡检任务，结果隔壁窗口的会话把它"抢走"执行了——那边没有这个需求的上下文，输出一堆驴唇不对马嘴的结果。

**pi-ultimate 的解法**：用 pi-subagents 把活派给子 agent（独立上下文、干完汇报）；定时任务用 sessionOnly 限定"仅创建它的会话执行"。[→ M7 文档](m7-subagents.md)

### 8. pi-schedule-status：定时任务状态全靠猜

**场景**："我的定时任务到底跑了没？下次什么时候跑？"——没有可视化，你只能翻日志、问 AI，甚至干等。

**pi-ultimate 的解法**：状态栏插件，任务名、ON/OFF、下次执行时间、执行中状态直接显示在 TUI 底部，一眼可见。[→ M8 文档](m8-schedule-status.md)

### 9. 工作流模板：值班巡检全靠人肉盯

**场景**：轮到你值班。你要盯着 bug 系统看有没有新 bug、盯着工单群看有没有新工单。发现一个，排查一个，修一个，通知一个。全程人肉，漏了还要背锅。

**pi-ultimate 的解法**：一套通用定时巡检工作流模板——定时拉任务源（TAPD/Jira/飞书项目都行）→ 去重 → 一单一子 agent 排查 → 修复 → 通知。无新单静默，敏感操作（改库、发布）必须经你确认。[→ M9 文档](m9-workflow-template.md)
